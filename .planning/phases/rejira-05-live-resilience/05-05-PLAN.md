  dsn: SENTRY_DSN,
  environment: process.env.NODE_ENV || 'development',
  tracesSampleRate: process.env.NODE_ENV === 'production' ? 0.1 : 1.0,
  replaysSessionSampleRate: process.env.NODE_ENV === 'production' ? 0.1 : 0,

    Sentry.replayIntegration({
      maskAllText: true,
      blockAllMedia: true,

    Sentry.browserTracingIntegration(),
    Sentry.httpClientIntegration(),
  ],
  ignoreErrors: [
    'NEXT_REDIRECT',
    'NEXT_NOT_FOUND',
    'AbortError',
    'ChunkLoadError',
  ],
  // Only send events in production
  enabled: process.env.NODE_ENV === 'production',
});

After creating, verify the existing `lib/observability/sentry.ts` `initSentry()` function. It currently calls `Sentry.init()` manually — this is the legacy pattern. With the config files, Sentry auto-initializes. Update `initSentry()` to be a no-op guard that only runs if config files didn't init:

In `apps/web/lib/observability/sentry.ts`, update `initSentry()`:
```typescript
export function initSentry(): void {
  if (initialized) return;
  // Sentry config files (sentry.client.config.ts / sentry.server.config.ts / sentry.edge.config.ts)
  // auto-initialize via @sentry/nextjs. This manual init is a fallback for environments where
  // the config files aren't auto-detected (e.g., some test runners).
  if (!process.env.SENTRY_DSN && !process.env.NEXT_PUBLIC_SENTRY_DSN) {
    return;
  }
  initialized = true;
  console.log('[observability] Sentry ready (config files handle initialization)');
}
```

Also update the `import 'server-only'` at the top of `sentry.ts` — this guard prevents it from loading on the client, which is incompatible with the client config file approach. Remove the `server-only` import since `captureError` is now called from both client and server error boundaries.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| App → Sentry | Trusted outbound: error data sent to Sentry's ingest endpoint. Risk: PII in error messages or extra context |
| App → PostHog | Trusted outbound: analytics events sent to PostHog. Risk: over-tracking user behavior |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-06 | Information Disclosure | Sentry extra context | mitigate | `captureError` only sends explicit context params; no DOM, no storage, no URL query strings. beforeSend callback configured in sentry.client.config.ts filters sensitive fields. |
| T-05-07 | Information Disclosure | PostHog properties | mitigate | `trackIssueEvent` only sends issueId, workspaceId, projectId — no title, no description, no comment text. PII-free by design. |
| T-05-08 | Data Integrity | Sentry disabled in dev | accept | Config files set `enabled: process.env.NODE_ENV === 'production'`. Developers see console logs instead. Acceptable — error tracking before production is unnecessary noise. |
