<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Vercel function → DB pool | The pg.Pool is per-function-instance. Vercel can spin up dozens of instances per second. The 10-conn-per-instance cap × instance count is the total |
| Sentry / PostHog outbound | Event payloads must not contain PII (no email, no description body, no token). The redactParams helper handles this |
| Playwright test env | The test env's Better Auth auto-verifies; the test must NOT depend on email delivery. RLS still applies; the test user is created in a fresh workspace each run |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-46 | Denial of Service | Connection pool exhaustion | mitigate | statement_timeout = 5s; pool size 10 per instance; pooler size 15; load test proves the budget; runbook documents the escalation path |
| T-04-47 | Information Disclosure | Sentry capturing SQL with sensitive params | mitigate | redactParams strips password/token/secret values; descriptions are not in SQL parameters (they are values, but the log entry shows the parameterized SQL, not the values) |
| T-04-48 | Information Disclosure | PostHog event payload leaking PII | mitigate | Event properties contain only ids and booleans (hasAssignee, hasLabel); no email, no name, no description |
| T-04-49 | Tampering | Playwright test env leaking data | mitigate | Each test run uses a unique email + workspace name; the test database is reset between runs (or the test seeds a fresh workspace) |
| T-04-50 | Spoofing | Slow-query warning could be weaponized | mitigate | Sentry.captureMessage is rate-limited at the Sentry SDK level; an attacker cannot flood the SDK with fake slow queries (they would need to actually trigger Drizzle queries) |
</threat_model>
