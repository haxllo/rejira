<objective>
The cutover. Every mutation that the UI performs (set status, change priority, assign, archive, bulk, create project, create cycle, create comment, mark notification read, save view, change role) now goes through a Next.js Route Handler that wraps the action in `withWorkspaceTransaction` and returns the result. Purpose: After this plan, every state change in the app is durable. Undo still works (revert the optimistic state). Retry works (re-run the most recent server action). lastError surfaces a user-safe mapped message with a Retry button. The Zustand store is the optimistic source of truth; RSC is the durable source.

**Step 1: Refactor the actions to drop the `tx` parameter.**

The actions in Plan 02 took `(tx, input)`. Standardize on `(input) => Promise<row>`. The route handler (task 1 step 3) opens the transaction. This refactor is mechanical:
- Remove the `withWorkspaceTransaction(workspaceId, async (tx) => { ... })` wrapper from each action
- Remove the `tx.` prefix from each `tx.insert(...)` / `tx.update(...)` / `tx.delete(...)` call (use `db.insert(...)` etc.)
- The action body becomes a single Drizzle write
- Remove unused imports of `withWorkspaceTransaction` from each action file

For each of the 7 action files (issues, projects, cycles, comments, notifications, saved-views, memberships):
- The action function signature changes from `(tx: typeof db, input: T): Promise<R>` to `(input: T): Promise<R>`
- The body changes from a `withWorkspaceTransaction` wrapper to a direct Drizzle call
- `track*` calls remain in the action (they are server-side; not affected by the change)

Pattern for each route (the issues route is the largest — the others follow the same shape):

```typescript
const SetStatusSchema = z.object({ op: z.literal('setStatus'), workspaceId: z.string().uuid(), issueId: z.string(), status: z.enum(['backlog', 'todo', 'in_progress', 'in_review', 'done']) });
const CreateIssueSchema = z.object({ op: z.literal('create'), workspaceId: z.string().uuid(), projectId: z.number().int().positive(), title: z.string().min(1).max(500), ... });
// ... one schema per op

const Schema = z.discriminatedUnion('op', [SetStatusSchema, CreateIssueSchema, ...]);

export async function POST(req: Request) {
  const user = await requireAuth();
  const body = await req.json();
  const parsed = Schema.safeParse(body);
  if (!parsed.success) {
    return NextResponse.json({ error: 'Invalid request', details: parsed.error.flatten() }, { status: 400 });
  }
  const { op, workspaceId } = parsed.data;
  
  // Defense in depth: workspaceId must match the user's session workspace
  const sessionWorkspaceId = await getActiveWorkspaceId();
  if (workspaceId !== sessionWorkspaceId) {
    return NextResponse.json({ error: 'Workspace mismatch' }, { status: 403 });
  }
  
  try {
    const result = await withWorkspaceTransaction(workspaceId, async (tx) => {
      switch (op) {
        case 'setStatus': return actions.setStatus({ workspaceId, issueId: parsed.data.issueId, status: parsed.data.status });
        case 'create': return actions.createIssue({ workspaceId, projectId: parsed.data.projectId, ... });
        // ... one case per op
      }
    });
    return NextResponse.json(result);
  } catch (err) {
    if (err instanceof DbError) {
      return NextResponse.json({ error: err.message, code: err.code }, { status: err.status });
    }
    const mapped = mapDrizzleError(err);
    return NextResponse.json({ error: mapped.message, code: mapped.code }, { status: mapped.status });
  }
}
```

Each route file:
- Defines a zod discriminated union with one variant per op
- The handler validates, checks the workspace match, opens the transaction, dispatches to the right action
- Errors are mapped to JSON responses with the right status code

The 7 route handlers are mechanical translations of this pattern. For the projects, cycles, comments, notifications, saved-views, and memberships routes, follow the same structure with the relevant ops.

**Step 1: Refactor `apps/web/lib/state/mutations.ts`.**

The new `apply()` accepts an async mutation function:

```typescript
export type MutationContext = {
  message: string;
  detail?: string;
  affectedIds: IssueId[];
  undo: () => void;        // revert optimistic state (does NOT call server)
  retry: () => void;        // re-run the server action (calls server)
  run: () => Promise<unknown>; // the new field — the actual server action
  viewAction?: { label: string; run: () => void };
  variant?: ToastVariant;
};

export function apply(ctx: MutationContext): void {
  if (STACK.length >= MAX_DEPTH) STACK.shift();
  STACK.push(ctx);
  setPending(ctx.affectedIds, true);
  hostBridge?.({ ...ctx, action: { label: 'Retry', run: ctx.retry } });
  
  // Fire the server call but don't await — the call site is fire-and-forget
  ctx.run()
    .then(() => {
      setPending(ctx.affectedIds, false);
    })
    .catch((err) => {
      setPending(ctx.affectedIds, false);
      recordError(err instanceof ServerActionError ? err.message : 'Something went wrong');
    });
}
```

The `retryLast()` re-runs `ctx.run()` and clears the error on success.
The `undoLast()` calls `ctx.undo()` (which reverts the optimistic state) but does NOT call the server.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → Server Action (HTTP) | The HTTP body is untrusted. The route handler validates the body with zod, re-checks workspaceId matches the session, opens a transaction, and calls the action |
| Server Action → DB | The action runs inside withWorkspaceTransaction; RLS evaluates against the verified session. Even if the HTTP layer had a bug, RLS would deny unauthorized writes |
| Client Optimistic State | The client's optimistic update is a UX concern; the server is the source of truth. If the optimistic state diverges from the server (e.g. RLS denied the write but the client already updated), the next RSC re-render corrects it |
