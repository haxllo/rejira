# Debug Session: ratelimit-table-missing-on-signup

## Symptoms

- **Expected:** User submits `/sign-up` form, Better Auth creates account, returns session, UI redirects into the workspace.
- **Actual (round 1):** 42P01 `relation "rateLimit" does not exist` — fixed by applying migration 0022.
- **Actual (round 2, current):** `POST /api/auth/sign-up/email` returns **422** with `{"message":"Failed to create user","code":"FAILED_TO_CREATE_USER"}`. The actual SQL error from `docker logs`:
  ```
  ERROR: column "role" of relation "user" does not exist at character 81
  STATEMENT: insert into "user" ("name", "email", "emailVerified", "createdAt", "updatedAt",
          "role", "banned", "twoFactorEnabled", "avatarColor", "status", "id")
          values ($1, ..., $11) returning *
  ```
- **User's hypothesis (refined):** Migration 0022 used snake_case columns; Better Auth core uses camelCase. **Half right, half wrong.** Investigation shows the current `supabase/migrations/0022_better_auth_schema.sql` *already* uses quoted camelCase (`"emailVerified"`, `"lastRequest"`, etc.) and those columns DO exist in the local DB. The real cause is different.
- **Timeline:** Round 1: `rateLimit` table missing locally — fixed by `supabase db push`-equivalent applying 0022. Round 2: 422 on every sign-up, in this dev environment. Sign-up has never succeeded.
- **Reproduction:** `curl -X POST http://127.0.0.1:3000/api/auth/sign-up/email -d '{"email":"d3@test.com","password":"testpassword12345","name":"D3"}'` → 422 every time. `rateLimit` row for `127.0.0.1|/sign-up/email` increments; `user` table does NOT receive a new row.

## Current Focus

- **hypothesis:** CONFIRMED via direct docker-log evidence. Better Auth's kysely adapter builds the user-create INSERT from the merged user schema (core + additionalFields + **all plugin fields**, with `defaultValue`/`transform.input` defaulting them in). The merged schema for this app includes the **admin plugin** (`role`, `banned`, `banReason`, `banExpires`) and the **twoFactor plugin** (`twoFactorEnabled`). The local `public.user` table (defined in 0022) only has: `id, name, email, emailVerified, image, createdAt, updatedAt, avatarUrl, avatarColor, status`. So the INSERT trips on the first missing column (`role` → 42703) before `banned` and `twoFactorEnabled` are even checked. After `role` is added, the next request will fail on `banned`, then on `twoFactorEnabled`. The `session` table will then fail on `activeOrganizationId` and `activeTeamId` (organization plugin) and `impersonatedBy` (admin plugin). The `twoFactor` table (TOTP secret storage) does not exist at all. Migration 0022 (uncommitted, untracked) defines the core tables but omits every Better Auth plugin's columns and tables. The AGENTS.md note "Better Auth schema is generated via `npx @better-auth/cli generate`" describes the *intended* workflow but was not followed when 0022 was hand-authored.

## Eliminated

- **Hypothesis: "Migration 0022 used snake_case columns; Better Auth expects camelCase."** Refined by reading the current 0022 file: it already uses quoted camelCase identifiers (`"emailVerified"`, `"lastRequest"`, `"createdAt"`, etc.). The local DB confirms: every column Better Auth writes to exists in the DB. The user's 42703 report for `lastRequest` and `emailVerified` is inconsistent with the local DB log — those columns are present and the failing INSERT does not reference them. The single 42703 on this checkout is `role`. *(Conclusion: the casing in 0022 is correct; the issue is missing plugin columns, not casing.)*
- **Hypothesis: "Missing `id` column."** The user table's `id text NOT NULL PRIMARY KEY` is present, and the failing INSERT does include `id` (value is generated by `getIdField`'s `defaultValue()` calling `generateId()`). So id is fine.
- **Hypothesis: "Drizzle is generating snake_case via `fieldName` mappings."** Confirmed there is no Drizzle auth schema. Better Auth's adapter is kysely (raw `pg.Pool` → `PostgresDialect`); Drizzle's `pgTable` for the app's `users` table is unrelated to Better Auth's `user` table.
- **Hypothesis: "Rate-limit storage is the failure point."** `public."rateLimit"` exists, the failing INSERT is into `public."user"`, and `rateLimit` rows are being written (`count=3` for the test sign-ups). Rate-limiter is working.

## Resolution

- **root_cause:** Migration `0022_better_auth_schema.sql` defines the five core Better Auth tables (`user`, `session`, `account`, `verification`, `rateLimit`) with the correct camelCase column names, but omits every column and table contributed by the enabled Better Auth plugins. The Better Auth plugins `admin` (adds `role, banned, banReason, banExpires` to `user`; `impersonatedBy` to `session`), `organization` (adds `activeOrganizationId, activeTeamId` to `session`; `teamSupport` is enabled because `server.ts:106` sets `team: { modelName: 'teams' }`), and `twoFactor` (adds `twoFactorEnabled` to `user`; new `twoFactor` table for TOTP secret storage) emit these fields as part of the runtime merged schema. The kysely adapter's `transformInput` (`@better-auth/core/dist/db/adapter/factory.mjs:99-141`) walks the full schema and includes the plugin fields in INSERT statements, which then 42703 against the incomplete local tables. The user's reported 42703 for `lastRequest` and `emailVerified` is not reproducible on this checkout (those columns exist in camelCase and the failing SQL does not reference them) — only the `role` 42703 fires here, with `banned` and `twoFactorEnabled` queued behind it. The casing in 0022 was already correct; the issue was exclusively the missing plugin columns/tables.
- **fix:** Edited `supabase/migrations/0022_better_auth_schema.sql` to (1) `ALTER TABLE` add the 5 missing `user` columns (`role text`, `banned boolean DEFAULT false`, `banReason text`, `banExpires timestamptz`, `twoFactorEnabled boolean DEFAULT false`), (2) `ALTER TABLE` add the 3 missing `session` columns (`activeOrganizationId text`, `activeTeamId text`, `impersonatedBy text`), and (3) `CREATE TABLE` the new `public."twoFactor"` table with `secret`, `backupCodes`, `userId` (FK to user), `verified`, plus indexes on `secret` and `userId`. All `ALTER TABLE … ADD COLUMN` use `IF NOT EXISTS` for idempotency. Applied to local DB by piping the file into the postgres container's `psql`. Updated the file's header comment to document the plugin column rationale.
- **verification:** `curl -X POST http://127.0.0.1:3000/api/auth/sign-up/email -H 'Content-Type: application/json' -d '{"email":"final@test.com","password":"testpassword12345","name":"Final Test"}'` → `200 {"token":null,"user":{...,"role":"user","banned":false,"twoFactorEnabled":false,"id":"9lwxErgqpNFyicQP3x6NVl9LlEtEaYQm"}}`. A second sign-up with `verify@test.com` also succeeded (`id=TR3GqP5DpW7hjya8gHn4wISOg9dY2iON`). `public.user` count went 1 → 3. `public.account` got the matching credential rows (providerId=`credential`, accountId=userId, password=bcrypt hash). Sign-in then returns `{"code":"EMAIL_NOT_VERIFIED"}` per the `requireEmailVerification: true` config — correct behavior. `docker logs <pg>` shows no new 42703 after the fix.
